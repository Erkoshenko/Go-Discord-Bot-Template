# Template-Go-Discord-Bot

## О шаблоне

За основу взят другой шаблон — базовый пакет организации проектов, разработанных на Go [https://github.com/golang-standards/project-layout\[\]](https://github.com/golang-standards/project-layout).

Все стандарты, используемые в шаблоне выше, относятся и к этому шаблону.

## Директории Go-бота

### `/cmd`

Основные приложения для текущего проекта.

Имя директории для каждого приложения должно совпадать с именем исполняемого файла, который вы хотите собрать (например, `/cmd/myapp`).

Не стоит располагать в этой директории большие объёмы кода. Если вы предполагаете дальнейшее использование кода в других проектах, вам стоит хранить его в директории `/pkg` в корне проекта. Если же код не должен быть переиспользован где-то еще - ему самое место в директории `/internal` в корне проекта. Вы будете удивлены тем, что могут сделать другие люди, потому выражайте свои намерения явно!

Самой распространённой практикой является использование маленькой `main` функции, которая импортирует и вызывает весь необходимый код из директорий `/internal` и `/pkg`, но не из других.

### `/internal`

Внутренний код приложения и библиотек. Это код, который не должен использоваться в других приложениях и библиотеках. Стоит отметить, что этот шаблон применяется самим компилятором Golang. Ознакомьтесь с [`release notes`](https://golang.org/doc/go1.4#internalpackages) Go 1.4 для более детальной информации. Также, вы вольны использовать более одной директории `internal` на разных уровнях структуры своего проекта.

Вы можете добавить дополнительное структурирование, чтобы разделить открытую и закрытую части вашего внутреннего кода. Такой подход не является необходимым, особенно для маленьких проектов, но позволяет сразу визуально оценить применение кода. Код самого приложения может находиться в директории `/internal/app` (например, `/internal/app/myapp`), а код, который это приложение использует - в директории `/internal/pkg` (например, `/internal/pkg/myprivlib`).

## Директории внутри `/internal`

В этом шаблоне `/internal` делится **по слоям**: каждая директория отвечает за один тип кода. Благодаря этому сразу видно, где искать нужное: команды в `commands`, события Discord в `handlers`, работу с данными в `repository`.

Зависимости идут в одну сторону:

```
main.go
  └─▶ handlers ─▶ commands ─▶ repository ─▶ database
```

Это значит, что `repository` и `database` ничего не знают про Discord, а `commands` не пишет SQL. Если вы видите импорт `discordgo` в `repository` или запрос `SELECT` в `commands`, код лежит не в том слое.

### `/internal/commands`

Слэш-команды бота: описание команды (имя, описание, параметры) и код, который выполняется при её вызове.

- `commands.go` — интерфейс `Command` (методы `Definition` и `Execute`), `CommandHandler` с реестром команд, регистрация команд в Discord и приём вызова команды: он находит нужную команду по имени и запускает её.
- `ping.go` и другие файлы — по одному файлу на каждую команду. Имя файла совпадает с именем команды.

Что здесь должно быть:

- описание команды и её параметров;
- проверка аргументов и прав вызывающего (например, «только администратор»);
- простые правила («сумма больше нуля»);
- текст ответа пользователю;
- вызовы репозитория, когда нужны данные.

Чего здесь быть не должно: SQL-запросов и кода подключения к базе. Они живут в `repository` и `database`.

Чтобы добавить команду:

1. Создайте файл `internal/commands/<имя>.go`.
2. Опишите в нём команду и функцию-обработчик.
3. Добавьте команду в список в `commands.go`.

### `/internal/handlers`

Обработчики событий Discord: бот запустился, пользователь вызвал команду, пришло сообщение, кто-то зашёл на сервер.

- `handlers.go` — структура `Handler`: собирает зависимости (репозитории, `CommandHandler`) и подключает события к сессии бота методом `RegisterAll`. Сейчас здесь обработчик `onReady`, который срабатывает при запуске бота.

Задача обработчика — **принять событие и передать его дальше**. Вызовы слэш-команд принимает `CommandHandler` из `commands`, поэтому здесь остаются остальные события: запуск бота, сообщения, вход на сервер. Логики самих команд здесь быть не должно, иначе файл быстро превратится в свалку.

Новое событие означает новую функцию-обработчик в `Handler` и одну строку `session.AddHandler(...)` в `RegisterAll`.

### `/internal/repository`

Всё, что связано с данными в базе. Репозиторий отвечает на вопрос «как это хранится и достаётся».

- `container.go` — структура `Repositories`, в которой собраны все репозитории, и конструктор `NewRepositories(db)`. Её создают один раз в `main` и передают туда, где нужен доступ к данным.
- `user_repo.go` и другие `<сущность>_repo.go` — по одному файлу на сущность (пользователь, товар, тикет). В файле лежат интерфейс (список методов) и его реализация на Postgres.

Зачем интерфейс: по нему в тестах можно подставить заглушку (mock) вместо настоящей базы. Примеры смотрите в `/examples`.

Правила:

- только SQL и преобразование результата в данные; никакого `discordgo` и текстов ответов;
- конструктор принимает пул соединений (`*pgxpool.Pool`), а не создаёт его сам;
- ошибки оборачиваются через `fmt.Errorf("...: %w", err)`, чтобы выше можно было проверить причину;
- «строки нет» (`pgx.ErrNoRows`) обрабатывается здесь, а не в командах.

Чтобы добавить репозиторий:

1. Создайте файл `internal/repository/<сущность>_repo.go`.
2. Опишите интерфейс, структуру с полем `db` и конструктор.
3. Добавьте поле в `Repositories` и создание в `NewRepositories` (`container.go`).

### `/internal/database`

Подключение к Postgres и больше ничего.

- `postgres.go` — создание пула соединений, его настройки (максимум соединений, время жизни), проверка связи (`Ping`) и закрытие.

Запросов к таблицам здесь быть не должно: это работа репозиториев. Параметры подключения (хост, порт, пользователь, пароль, имя базы) берутся из окружения (`.env`) и не записываются в код.

### `/examples`

Примеры для разработчика, не часть бота. Удаление этой директории никак не повлияет на работу.

- `mock_example.go` — пример заглушки (mock) репозитория: структура с теми же методами, что у настоящего репозитория, но без базы.
- `repository_test_example.go` — пример теста репозитория.

Важно: Go запускает тесты только из файлов, имя которых заканчивается на `_test.go`. Чтобы использовать пример, скопируйте его рядом с проверяемым кодом и переименуйте (например, `internal/repository/user_repo_test.go`). Тесты принято хранить рядом с кодом, а не в отдельной директории.

### `/configs`

Шаблоны файлов конфигураций и файлы настроек по-умолчанию.

Поместите файлы конфигураций `confd` или `consul-template` сюда.

### `/pkg`

Код, который не привязан к боту и мог бы пригодиться в другом проекте (например, вспомогательные функции форматирования). Если такого кода нет, директорию можно не создавать.

### `.env`

Секреты и настройки окружения: токен бота, параметры подключения к базе.

- Файл **не должен попадать в git**. Добавьте `.env` в `.gitignore`.
- Храните в репозитории `.env.example` с теми же ключами и пустыми значениями, чтобы другой разработчик знал, что нужно заполнить.
- Если токен бота когда-либо попал в публичный репозиторий, сбросьте его в Discord Developer Portal.

## Кратко: куда класть код

| Что вы пишете | Куда класть |
| --- | --- |
| Новая слэш-команда | `internal/commands/<имя>.go` |
| Реакция на событие Discord | `internal/handlers/` |
| SQL-запрос, работа с таблицей | `internal/repository/<сущность>_repo.go` |
| Подключение к базе, настройки пула | `internal/database/` |
| Пример или заготовка для теста | `examples/` |
| Тест настоящего кода | рядом с кодом, файл `*_test.go` |
| Токен, пароли | `.env` (не в git) |

## Когда структура перестаёт подходить

Раскладка по слоям удобна, пока команд и таблиц немного. Когда фич станет много (экономика, модерация, тикеты) и для правки одной из них придётся открывать `commands`, `handlers` и `repository` одновременно, переходите на раскладку по фичам: у каждой возможности бота своя директория (`internal/economy/`) с собственными `repository.go` и `commands.go`. Переезжать можно постепенно, по одной фиче за раз.
